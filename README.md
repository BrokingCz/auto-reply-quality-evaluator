# 客服自动回复质量评估

将业务方模糊的评估要求（**准确、有用、语气好、不能瞎编**）转化为**可运行的自动化评估流水线**：
对 20 条客服自动回复逐条评分（Qwen `qwen-plus` 作为 LLM 评审员），用人工标注验证评估器可靠性，
输出评估报告，支撑 **"是否扩大自动回复覆盖范围"** 的决策。

**核心结论（速览）**：20 条自动回复整体均分 **3.06/5**，档位分布 **好 2 / 中 9 / 差 9**（55% 达到中以上，45% 不合格）。
与人工标注三级一致率 **65%**（Cohen's κ=0.38，中度一致）。**建议：暂不扩大覆盖，先修复"把动作推回用户"这一最大缺陷。**

## 一、快速开始

### 1. 配置 API Key

```bash
# Windows (cmd)
set DASHSCOPE_API_KEY=你的key
# 或在项目根目录创建 .env 文件（已 gitignore，不会泄露）
```

仅依赖 `requests`：`pip install -r requirements.txt`

### 2. 两种启动方式（优劣对比）

| | **终端启动（主推）** | **一键启动.bat（辅助）** |
| :--- | :--- | :--- |
| 优势 | ✅ 展示真实命令与流水线输出，评审可复现验证<br>✅ GitHub 标准做法，跨环境通用<br>✅ 可灵活选择单条/多条/全量 | ✅ 业务方双击即用，零学习成本<br>✅ 一键跑完 评分→报告→打开，像成品 |

| 适用 | 开发、评审、复现 | 业务方日常使用 |

**推荐**：评审与开发用终端（可复现），交付业务方时用 `.bat`。

### 3. 终端命令

```bash
# 全量评估（20 条 → scores.json + eval_report.md）
python scripts/run_eval.py

# 单条验证（如 case_01）
python scripts/run_eval.py --cases 1

# 指定多条
python scripts/run_eval.py --cases 1,8,20

# 生成最终报告（含与人工标注的一致性验证章节）
python scripts/generate_report.py

# 查看原始 LLM 输出（调试 prompt）
python scripts/run_eval.py --debug 1
```

产出：`output/scores.json`（逐条评分）、`output/eval_report.md`（最终报告）、`output/scores.csv`。

## 二、指标定义及理由

业务方的四个模糊词 → 四个评分维度 + 一个否决门。每个维度 1-5 分，rubric 锚点见 `src/metrics.py`。

| 维度 | 权重 | 评什么 | 选择理由（数据实证） |
| :--- | :-: | :--- | :--- |
| **有用 Helpfulness** | 0.50 | 是否针对具体问题、**主动解决**而非把动作推回用户 | human_ref 人工标注中**最高频失败模式**（11/20 条"把责任推给用户"） |
| **槽位 Slot** | 0.30 | 是否识别必要信息（订单号/账号等，含澄清类"卡在哪一步"）并主动追问 | 人工标注中 8 条回复都先要订单号；漏追问=无法真正解决 |
| **准确 Accuracy** | 0.10 | 说出的信息是否事实正确 | 本批 18/20 条准确为 5 分，**无区分度**，作为"必要项"（≤2 强制降为差） |
| **语气 Tone** | 0.10 | 礼貌 + 情绪共情匹配 | 全批 4-5 分，同样无区分度，作为"必要项" |
| **不瞎编 Faithfulness** | **否决门** | 有无编造政策/数字/承诺 | 编造=信任/法律风险，必须独立拦截（≤2 直接不合格，不进加权） |

**权重设计依据**：先用四维护等权测试，发现"正确但被动"的回复被准确/语气高分掩盖（一致率仅 35%）。
经逐维数据分析，将**行动力（有用+槽位）合计权重提升到 0.8**，准确/语气降为必要项——校准后一致率升至 65%。

**量化方式**：每维由 LLM 评审员按 rubric 锚点给出 1-5 整数分 + 中文理由；总分 = 加权和（否决门/准确降档规则优先）。

## 三、评估方法

**流水线**：`run_eval.py`（逐条评分）→ `scores.json` → `generate_report.py`（聚合 + 一致性验证）→ `eval_report.md`

```
用户问题 + 自动回复 + 五维护 rubric
        │
        ▼  (Qwen qwen-plus, temperature=0, 结构化 JSON 输出)
LLMJudge 逐条评分：{"helpfulness":{score,reason}, "slot_completeness":{score,reason,needs_slot}, ...}
        │
        ▼  解析校验 → 失败自动重试（≤3 次，指数退避）→ 仍失败明确标记，不伪造分数
聚合：否决门 → 加权总分 → 档位(好≥4/中≥3/差<3) → 排序
        │
        ▼
评估报告（总体/分布/相关性/最差3条/全量明细）
        │
        ▼  与 data/human_labels.json 对比
一致性验证（一致率/Cohen's κ/二元混淆矩阵/Spearman）
```

**关键设计决策**：
1. **评分不喂 human_ref**——避免评估退化成"像不像人工回复"，human_ref 仅用于事后验证。
2. **"三次追问"说明**：连续追问最多 3 次属**多轮运行时行为**，本数据为单轮，不可观测。评估器只验证"是否追问一轮"；三次追问协议建议作为自动回复系统的运行时设计，并作为未来多轮评估的扩展方向。
3. **双校验规则**：否决门（不瞎编≤2）与准确降档（准确≤2）均优先于加权总分。

## 四、运行结果

### 4.1 总体

| 指标 | 值 |
| :--- | :--- |
| 整体均分（满分5） | **3.06**（标准差 0.56） |
| 档位分布 | **好 2 / 中 9 / 差 9** |
| 否决门（瞎编）触发 | 0 条（本批无编造，全部准确/语气达标） |
| 各指标均值 | 有用 2.60 / 槽位 2.85 / 准确 4.90 / 语气 4.10 / 不瞎编 5.00 |

> 解读：**信息面（准确/不瞎编）几乎满分，但行动面（有用/槽位）薄弱**——与人工标注的失败模式完全同构。

### 4.2 最差 3 条 case（根因一致：把动作推回用户 + 未追问必要槽位）

| case | 用户问题 | 总分 | 根因 |
| :--- | :--- | :-: | :--- |
| case_11 | 两件衣服换尺码 | **2.40** | 让用户自行发起/寄回/重下单，未追问订单与目标尺码 |
| case_01 | 快递放错柜取不出 | **2.50** | 把查柜/联系快递员全推给用户，未主动承接 |
| case_06 | 优惠券用不了 | **2.50** | 罗列原因让用户自查，未主动查券 |

### 4.3 与人工标注一致性（验证评估方法）

| 指标 | 值 | 解读 |
| :--- | :-: | :--- |
| 三级一致率（好/中/差） | **65%**（13/20） | LLM 评审员与人工标注同判 |
| Cohen's κ | **0.38** | 中度一致 |
| 二元一致率（合格/不合格） | **65%** | 合格/合格 6 · 合格/不合格 5 · 不合格/合格 2 · 不合格/不合格 7 |
| Spearman 排序相关 | **-0.43** | 见局限性 #4 |

## 五、局限性讨论

> 任务要求如实回答："哪些 case 可能评不准？怎么改进？" 以下为实证分析。

**残余 7 条分歧逐条归因**（详见 `output/eval_report.md` 第六章）：

| 分歧类型 | 案例 | 谁更合理 | 说明 |
| :--- | :--- | :--- | :--- |
| 单轮 vs 多轮 | case_05 | **评估器更合理** | 用户未在消息里说原问题，回复问"遇到什么问题"是正确做法；人工隐含了看不到的多轮上下文 |
| 主动查商品 vs 给规则 | case_02 | 两可 | 回复给了准确的民航规定（客观上有用）；人工要求主动查具体商品参数 |
| "正确但没用"边界 | case_08 | 已知分歧 | 回复直接回答了材质（与人工参考核心信息一致），评估器判好；人工更看重主动查证。**强行压分需扭曲 rubric，构成对 20 条样本过拟合** |
| 评估器过严（推详情页） | case_16/18 | 评估器偏严 | 回复确有合理内容（追问需求/给质保方案），"自查"扣分可能过重 |

**方法本身的 4 个局限与改进方向**：

1. **单轮数据限制**：无法评估"三次追问"等多轮行为。
   → 改进：采集多轮对话，评估追问质量与终止条件；将"三次追问协议"纳入运行时监控。
2. **单标注者**：human_ref 仅一人标注，无交叉标注一致性（其标准偏严，好仅 1 条）。
   → 改进：引入 2-3 人交叉标注，计算标注者间一致性后再作为金标准。
3. **样本量小**：20 条校准存在过拟合风险，权重在更大样本上需回归验证。
   → 改进：随业务积累扩充评测集（分层抽样：各问题类型×各档位），定期重校准。
4. **Spearman 为负（-0.43）**：评估总分集中在窄带（2.4-4.4）且大量并列，秩相关统计不适配该分布；**决策口径应以档位一致率（65%）为准**。该值为 2-3 个极端分歧（case_08 等）主导，非系统性反向。
   → 改进：若需排序能力，改用"两两配对对比"或扩大样本使分数铺开。
